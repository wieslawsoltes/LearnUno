# Source-informed curriculum priorities

## Evidence and method

The feature inventory scans the same Uno revision as the chapter corpus: `e1292e0d87f9d38c9f3a120c69f0200b3c0999c1`. It examines 19,024 C#/XAML files and 420 Markdown documents. Public class declarations outside `Uno.UI/Generated` are matched to distinct sample XAML files, after XML comments are removed. The current result contains 559 discovered public UI-area types and 1,542 sample XAML files.

This is a lexical inventory, not a semantic public-API scan, market telemetry or proof that every discovered type is a finished control. Handwritten declarations, sample presence, test presence, target support and documentation are different evidence. Class declarations alone do not establish implementation parity. The feature-map page labels unmatched topics **reference-only**, not completed lessons.

Sample frequency is used to find high-impact reading gaps, then editorial judgment prioritizes ordinary application tasks. For example, ScrollViewer occurs in 297 sample files, CheckBox in 122, Image in 113, ComboBox in 130, VisualState in 84, ToggleSwitch in 27 and MenuFlyout/Flyout in their dedicated samples. Exact current counts and links are generated by `scripts/feature-survey.mjs`; values are not hard-coded into UI claims.

The scan is reproducible from the pinned checkout. Each displayed implementation record includes its file hash in the downloadable JSON, and links point to the immutable revision. Source evolution and the pinned 6.7 runner remain separate: a 7.x source contract must not be silently presented as a capability of the 6.7 teaching runtime.

## Learning priorities

| Priority | User task | Material delivered |
| --- | --- | --- |
| P0 | Build a form, choose values, commit a draft | Existing input/Toolkit/validation paths; keyboard-first forms and selection semantics design lessons |
| P0 | Keep content readable and reachable | Bounded scrolling, image lifecycle, semantic themes and density |
| P0 | Organize a real application | DI scopes/factories/options, navigation parameters/journals/guards, shared command behavior |
| P1 | Maintain a data workspace | Paging, request/content state, conversion, versioned edits, notification strategies, bounded undo/redo |
| P1 | Adapt and recover | List/detail mockup, inline status, cancellation, retry, retained content |
| P2 | Specialized controls and native APIs | Reference-only gaps retained in the inventory: richer trees/grids, media, printing, drag/drop, sensors, native hosting and tooling |

“Cover all topics” is treated as an auditable curriculum direction. This release does not relabel source-only entries as authored or executable lessons. The map makes the next work discoverable rather than hiding it behind a completion percentage.

## New design lessons

Eight independent UI design lessons add 32 guided steps, 24 concrete design checkpoints, eight interactive HTML mockups, primary documentation links, pinned source/sample cards and sixteen real-Uno C# variants. They cover scrolling, checkbox/radio/switch semantics, command menus, status-with-content, keyboard forms, adaptive list/detail, images and theme/density.

A mockup is explicitly labelled HTML and is not an alternative Uno renderer. It lets learners inspect a design choice; the real Uno tab executes a separate C# program. Width, text scale and density controls preserve in-progress input; selection remains keyed during resize. Steps use focused navigation and revealable reasoning. No arbitrary code from shared URLs or source links is evaluated.

The introductory design advice is grounded in the Microsoft Forms, focus, selection, progress, image and theme guidance linked from each lesson, and the matching Uno source. It is not a claim of pixel-identical WinUI styling or complete cross-platform assistive-technology validation.

## Release gates

The compilation matrix includes all 90 core lessons, six recovered data workshops and eight new UI-design lessons: 104 learning units, 208 starter/solution executions and 174 C# variants. The difference is the existing XAML labs. Independent workshop completion is not silently added to the core progress total.

The normal CI pipeline must compile the full matrix against actual runner metadata, execute every variant in the real browser host, test all routes and check the deployed Pages URL. Node models or mockup screenshots alone do not establish runtime verification. Required tests must not be weakened to make a candidate publish.
